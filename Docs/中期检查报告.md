## 三、 遇到的技术障碍与解决方案

### 3.1 设计期已规避的障碍（方案级）

| 序号 | 技术障碍 | 解决方案 | 状态 |
| :---: | :--- | :--- | :---: |
| 1 | SysTick 软件计时在进入 STOP 低功耗后停摆、时间丢失 | 改用片内 RTC（LSE）走时，RTC 独立后备域，休眠持续走时 | 已解决 |
| 2 | STM32F1 硬件 I2C 外设存在总线死锁缺陷 | OLED 改软件模拟 I2C，MPU6050 保留硬件 I2C1，双总线物理隔离 | 已解决 |
| 3 | 最高优先级任务忙等轮询会饿死其他任务 | Task_Power 改为 500ms 周期 + 事件标志，唤醒即让出 CPU | 已解决 |
| 4 | STOP 模式下编码器旋转（TIM2）无法唤醒 | 唤醒源改用 EXTI：编码器按键 + MPU6050 抬腕中断 | 已解决 |

### 3.2 真机联调阶段定位并修复的缺陷（本次中期重点）

联调阶段集中暴露了三个真机才复现的问题，均已定位根因并修复、编译通过
（arm-none-eabi-gcc，RAM 74.96% / FLASH 72.20%），等待真机复测确认。
完整排查过程另见 [`Docs/故障排查记录.md`](故障排查记录.md)。

**缺陷 A：蓝牙"只能收不能发"、疑似连不上手机。**
- 根因（主）：无操作 10s 即进 STOP，而 STOP 下 USART2 无时钟——手表既不推
  送状态也收不到命令；但 JDY-31 模块独立供电，手机仍能连上模块，于是现象
  恰好是"连得上却没有数据"。测试时低头操作手机的几秒，手表已经睡了。
- 根因（次）：HAL 的 UART 收发共用一把锁，中断里重挂接收若撞上任务发送持锁
  会返回 BUSY，接收从此断链；过载/帧错误(ORE/FE)后 HAL 也不会自动恢复接收。
- 修复：收到任一蓝牙字节即刷新活动计时（会话期间不休眠）；新增
  `HAL_UART_ErrorCallback` 清错并重挂；`Task_Comm` 加 RX 看门狗兜底；STOP
  唤醒后 `AbortReceive`+重挂清残留。**使用提示**：JDY-31 是经典蓝牙 SPP，
  iPhone 不支持、须用 Android，且系统配对后要在串口 App 里主动建立 SPP 连接。

**缺陷 B：开机偶发卡在 TIME 页约 10s、且熄屏不响应。**
- 根因（不熄屏）：MPU6050 运动中断每触发一次就刷新一次"活动计时"，佩戴/
  手持状态下手一直微动、中断以采样率级别反复触发，空闲计时永远清零 → 永不熄屏。
- 根因（卡死）：PA4 原为浮空输入 + 上升沿中断，接触不良/线松时引脚悬空引发
  EXTI 中断风暴，把所有任务饿死；且 Task_Sensor(优先级3) 高于 Task_UI(2)，
  硬件 I2C 异常时 HAL 每次调用空转 ~25ms 等超时并立即重试，也会饿死 UI。
- 修复：运动中断改为**只计数、不刷新活动计时**（熄屏计时只由按键/编码器/蓝牙
  数据触发，抬腕唤醒不受影响）；PA4 改内部下拉杜绝浮空中断风暴；Task_Sensor
  连续 5 次 I2C 失败后退避 200ms；进 STOP 序列加临界区并清 SysTick/PendSV 挂起。

**缺陷 C：STOP 休眠后抬腕无法唤醒，只能靠编码器按键唤醒（两轮排查）。**
> 本缺陷是本阶段最具代表性的调试案例，记录两轮定位过程如下：
- 首要判据：**按键能唤醒**即证明 EXTI→STOP 唤醒链路本身完好，问题必在
  "MPU6050 到底有没有产生 INT 脉冲"这一上游环节。
- **第一轮**（判断有误）：怀疑 INT 处于锁存模式、代码未读 `INT_STATUS(0x3A)`
  清除导致 PA4 长期为高、进 STOP 无新边沿。据此改为非锁存脉冲模式并放宽 DLPF
  低通（原 5Hz 低通把抬腕动作能量滤掉了）。**真机复测仍唤不醒。**
- **第二轮**（查阅数据手册与多方验证实现后定位真正根因，两点）：
  1. **缺信号通路复位**：MPU6050 运动检测的标准配方要求先写
     `SIGNAL_PATH_RESET(0x68)=0x07` 复位加速度信号通路，否则运动检测前置的
     高通滤波器残留旧状态、阈值比较器永不翻转，INT 根本不产生。此步此前遗漏。
  2. **脉冲模式反而更不可靠**：第一轮改成的 ~50µs 脉冲太短，经面包板杜邦线与
     引脚输入电容后 STM32 EXTI 常常抓不到上升沿。应改回**锁存模式**
     (`INT_PIN_CFG=0x20`)——INT 触发后保持高电平直到读 `0x3A`，给 EXTI 一个
     稳定明确的电平+边沿。
- **最终修复**：补齐信号通路复位 + 锁存模式 + DLPF 放宽 44Hz；配套在清醒时由
  Task_Sensor 每帧读一次 `0x3A` 重新"布防"、进 STOP 前与唤醒后各清一次，使锁存
  既可靠触发又不会卡住。同时在传感器页新增 `INT:` 计数作为链路自检窗口
  （晃动模块该数应增长），并把运动阈值下调（20→现场标定）提高灵敏度。
- 经验教训：**"按键能醒、抬腕不醒"应第一时间把问题二分到 MCU 唤醒链路之外、
  聚焦传感器出中断这一环**；外设手册里"看似可省"的复位/初始化步骤（信号通路
  复位）恰恰是功能不工作的元凶；短脉冲中断在面包板上不可靠，能锁存就锁存。

**附带修复（严重，与上述三问题无关）：一键开机自锁失效。** 联调中发现全工程
无任何代码拉高 PA8(PWR_HOLD)、且被初始化为低电平，脱离 ST-Link 用电池供电时
一松开电源键系统立即断电。已在 `SystemClock_Config` **之前**（LSE 起振可达数秒）
把 PA8 配置为输出并拉高。*说明：经与测试沟通，验收阶段不强制要求一键开关机，
仅需上电后抬腕/按键唤醒正常即可；该修复保留但不作为必测项。*

### 3.3 设计取舍（非缺陷）

| 事项 | 说明 |
| :--- | :--- |
| 休眠(STOP)期间步数不累加 | STOP 下 CPU 停摆，`Task_Sensor` 不运行属预期。经权衡**保留 STOP 深度低功耗**，将"低功耗"与"计步"作为两个独立演示项：熄屏深睡省电、抬腕/按键唤醒后继续计步 |
| 计步不依赖硬件重低通 | 为让运动中断可触发，运动检测路径 DLPF 放宽到 44Hz；计步侧改由软件 8 点滑动平均平滑，精度不受影响 |
